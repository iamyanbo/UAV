# Retired v3 benchmark proposal — historical only

This was an operator-selected integration plan, not a field-standard research baseline. It is no longer staged as worker guidance or enforced by the runtime. Its MuJoCo preflight remains a useful engineering note, but the active v4 research contract lets the agent select the method, environment and evaluation for its own claim. Do not treat the receipt format below as a requirement.

The current MuJoCo scenes in research/model_program/sim_quadrotor.py are engineering diagnostics. They train real weights, but their five handwritten primitive layouts, wrench actions, simple teacher and shared waypoint information cannot establish a navigation or world-model result. Earlier metrics remain useful for debugging and may be reused as a warm start. They are not a published baseline or independent held-out environment.

The cached upstream is `.research-upstreams/mujoco-drones-gym/`, an intact copy of [MuJoCo-Drones-Gym](https://github.com/tau-intelligence/MuJoCo-drones-gym) at commit `ca170dc6760d422e47ef46fb3af46f8cd20410eb`, corresponding to [arXiv:2606.08039](https://arxiv.org/abs/2606.08039). The upstream has a Crazyflie 2.x airframe, four motor RPM commands, a PID reference, camera observations, obstacles and waypoint/racing tasks. Its visual layouts may still be limited; using the repo alone is not representative evidence of broad scene generalization. `gym-pybullet-drones` is another published motor-level reference. UAV-Flow/Colosseo is the relevant released dataset/evaluator for fine grained language-conditioned action, and should be used when semantic control is claimed. FlowPilot is a close world-action model comparison, but importing its name does not reproduce its computation.

Verified local preflight: Python 3.10 imports Gymnasium 1.0.0, MuJoCo 3.9.0 and the pinned upstream. `BaseAviary` with `vision_attributes=True`, `obstacles=True`, `obs_type=RGB`, `act_type=RPM`, `Physics.MJC`, `sim_freq=240`, `ctrl_freq=48` ran 48 PID-controlled steps. An onboard image had shape `(1,48,64,3)` with nonzero variance, and the airframe moved from z=0.115 to z=0.165 m in one simulated second. This confirms the dependency works here; it is a smoke result, not a navigation score.

## Immediate work in the existing program

1. Read the upstream environment classes and controller. Preserve current model code/weights where useful. Implement an adapter that uses the upstream package's motor-level physics, camera and controller. Do not replace the imported package with another local scene generator and call it the benchmark. Do not silently feed privileged waypoint or obstacle truth to a deployed visual actor.
2. Execute `run_check` on a saved `benchmark_*.py` adapter script. Save `BENCHMARK_SMOKE.json` with `upstream_revision`, `adapter_path`, `metrics_path`. Metrics JSON needs `steps`, `sim_seconds`, `rgb_shape`, `rgb_variance`, `motor_rpm`. This receipt must come from the upstream package, not invented labels. Fix import/API issues before moving on. An implementation milestone is accepted only after this run.
3. Choose a named upstream task, document the exact sensor/action interface, controller, physics mode and parameter changes. Reproduce its included PID/control behavior, then port the existing visual prediction/action models. Describe all differences from the closest paper architecture. The label “JEPA reference” does not itself mean SkyJEPA was reproduced.
4. Evaluate matched models on independent scenes or assets, not merely different episodes in the same five layouts. Save a split manifest before testing. Train the proposed and nearest published/reproduced model on the same observations, actions, data and budget. Include an ablation. Score mission success, contact/clearance, inference and capture-to-applied-command timing while physics advances. Run actual input perturbations for vision, executed action, language when claimed, and privileged-label leakage; comparing a model with itself on unchanged inputs is not a probe.
5. For a representative claim, write `BENCHMARK_EVALUATION.json`: `upstream_revision`, `upstream_paper`, `task_class`, `sensor_interface`, `action_interface`, `controller`, `physics_mode`, nonempty disjoint `train_scenes`, `validation_scenes`, and at least two distinct `test_scenes` or assets, `split_manifest_path`, `runner_path`, `methods` containing `proposed`, `published-or-reproduced`, `ablated` roles each with a metrics path, `rollout_log_path`, `latency_log_path`, `counterfactual_probe_path`, `comparison_protocol`, `nearest_method_url`, `contribution_boundary`, `architecture_comparison_path`. Each method needs at least 20 completed episodes across at least three seeds, with success, collision and p95 action-age measurements. The architecture comparison must trace the closest paper's encoder, temporal state, predictor, action head, objective and training data against actual code, not just compare names. The perturbation JSON must contain a `perturbations` array with `kind` entries for `vision`, `action`, `privileged`, each recording distinct `input_hash_before`, `input_hash_after` and a measured `output_delta`. If language is a scientific claim, add `semantic_claim: true` and `semantic_benchmark_source` with the released evaluator/dataset and a measured implementation.

The runtime checks paths, revision and that benchmark scripts ran successfully. The lead and verifier must inspect model code, split construction and raw outputs for actual fidelity. A complete JSON receipt cannot certify novelty, physical safety or sim-to-real transfer. If the published environment is too visually limited for the intended claim, add a stronger released scene set and report that separately; keep the Crazyflie motor-dynamics result as one tier of evidence.
