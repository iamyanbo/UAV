This is a finite, user-requested hypothesis investigation in the existing UAV navigation direction. It is unverified input, not an accepted finding, an approved implementation, or a replacement mission. Keep normal Spark orchestration, executor preflight, worktree isolation, verifier and evidence handling. Do not change provider, launch another supervisor, interrupt an outstanding task, bypass an approval, or connect a physical aircraft. The Spark research model is distinct from any small on-device model being evaluated.

First retrieve the closest prior methods and decide whether the specified training/information-flow difference survives. If it does and dependencies are accessible, implement the smallest discriminating pilot through the normal task approval path. Do not end with another generic literature summary when a valid pilot is feasible. Conversely, if a functional equivalent already exists, return the evidence and reject or clearly narrow the claim; do not force a positive result or substitute a new name for the same mechanism.

These are planning bounds, not runtime-enforced timers or promises. A single useful full-method comparison can take longer: record why. Avoid repeated dependency debugging; after two materially different failed access/setup attempts, preserve the blocker and return so other ready investigations can proceed. Do not quietly replace an unavailable experiment with fabricated features.

### What a novelty check must establish

Retrieve actual papers, supplements and released code where possible. Preserve exact title/identifier agreement, version, publication/retrieval dates, URL, relevant section/code path, access failures, and enough excerpt context to audit the interpretation. Check robotics/manipulation/control/active-learning equivalents, not only UAV terminology. Report sensor inputs, privileged training state, latent architecture, outputs, control interface, objective and supervision, memory, operating frequency, hardware, and evaluation protocol. "Not reported" is not "not implemented."

Give the closest counterexample every advantage. State which component is already known, the precise residual difference, and whether that difference changes an algorithm or training objective rather than only the domain/backbone. Use statuses: exact overlap, functional equivalent, component overlap, unresolved, or apparently distinct within the explicitly searched boundary. Never claim absolute novelty or that all literature was covered. Only propose training if there is a concrete implementation question worth answering.

### Data, compute and latency

Probe the available 3060 Ti and installed packages. Target a small trainable head/predictor, sequential jobs, frozen/cached encoder features for training, and at most 60% of visible local CUDA memory (about 4.9 GiB on an 8 GiB device); the worker runtime enforces this ceiling for Python subprocesses. Start with CPU physics or an already installed simulator. Do not pretrain a large JEPA, fine-tune an entire Qwen VLM, set up a large renderer stack, or fetch multi-gigabyte new checkpoints merely to keep busy. Prefer existing assets; keep new download needs explicit and bounded (suggested initial total below 2 GiB per candidate).

Cached-feature training is acceptable if the cache is derived from real model invocation on identified images with checkpoint/config hashes. It does not establish online latency. Measure batch-one end-to-end latency including visual preprocessing, encoder/prefill, transfers, queue delay, decision head and controller; report head-only numbers separately. CUDA timing must synchronize. If a VLM's decoder generation is removed, its visual encoder and language-model forward pass still cost time. Do not describe a scalar-only or random-feature prototype as a working visual JEV. Record true weights independently of the Spark transport model alias.

### Evidence checks that cannot be skipped

Prior ledger outcomes are hypotheses/evidence leads, not reusable scientific ground truth. In particular, do not propagate the earlier H1/H2 mixed-metric comparison, almost-constant binary targets, or unsealed feature/implementation claims without auditing the original executable artifacts. Action classification accuracy is not closed-loop navigation success. Waypoint L2 error is not collision ground truth. Predicting a deterministic threshold does not show the model learned safety. A smaller error metric is not a new navigation method.

Keep oracle mesh/dynamics/future labels on the training/evaluation side; the deployed policy sees only its declared observations. Check class balance, trivial baselines, units, label leakage, disjoint scene/episode splits and unseen dynamics. Test metric routines including tied-score AUC and empty/constant-class cases. Use independent episodes, not correlated frames, as statistical units. Prefer three seeds if the pilot budget permits; otherwise label the result single-seed exploratory. Reuse the exact same observations, action candidates, controller, training examples and evaluation distribution in mechanism ablations.

A synthetic physics or image-rendered pilot is valid mechanistic evidence if honestly labelled. It is not OpenFly performance, full flight dynamics, real-scene reconstruction quality, or sim-to-real validation. A collision rate requires an independent geometry/physics oracle; a reconstruction cannot certify its own missing obstacles. Do not compare results to paper headline numbers unless protocols actually match.

Return source collision verdict, implementation/commands, data/checkpoint provenance, raw metrics and tests, failures, compute/latency, remaining sim-to-real assumptions, and a plain-language explanation. Seal code and results through the normal evidence path. If blocked or refuted, that is the result; do not invent an improvement. Ask the lead to close this finite plan after interpreting the pilot, or specify a genuinely new evidence-backed follow-up. Leave the other ready candidates available and then let the ordinary continuous Spark orchestrator choose subsequent research.
